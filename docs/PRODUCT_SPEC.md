# Спецификация продукта: Jigas — Граф денег

Версия 1.3 · 23.09.2026 · статус: принятый контракт, реализация и приёмка ведутся отдельно. Приняты React/Vite + Cytoscape.js для графа, объединение blueprint-ов и приоритетные изменения второй волны: объяснения правил, читаемость графа, ранний сценарий запроса данных и маршруты с датами.

Основания — [blueprint Astra](../HackAlem_AI_Research_Architecture_Blueprint.md), [первое сравнение](BLUEPRINT_COMPARISON.md) и [вторая волна с измерениями и источниками](SECOND_WAVE_RESEARCH.md). Технические контракты и правила: [SPEC 1.4](SPEC.md). Очередность и реестр задач: [PLAN 1.3](PLAN.md). При расхождении исследовательских предложений реализация следует этим спецификациям.

**Дополнение release-review, 23.09.2026:** [HA-18](https://trello.com/c/3JL9XkLK) добавляет в существующее описание кластера первый узел для проверки по P, его роль, степени и наблюдаемые вход/выход. Изолят и ограничения группы описываются явно; лидер не объявляется организатором. Это необязательная текстовая доработка по SPEC §6.1, без новой метрики, поля или экрана. Её можно подготовить независимо после HA-04.2/HA-05.1; включать только после P0/React/HA-17 с проверкой до freeze. Основной контракт остаётся версии 1.3.

## 1. Пользователь и результат

Пользователь — AML-аналитик банка. Он получает ограниченный граф переводов вокруг известных seed-клиентов и должен выбрать, кого проверять следующим, увидеть основания и определить, какие данные запросить для проверки гипотезы.

Результат MVP: один локальный запуск из трёх Parquet создаёт `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, строгий `report.json` и готовый React-интерфейс (`index.html`, `report.html`, assets), доступный через корень localhost. Все 2 248 клиентов доступны в таблицах и поиске. Выводы обозначают структурные гипотезы для проверки.

## 2. Пользовательский сценарий

1. Указать папку с `nodes.parquet`, `edges.parquet`, `transactions.parquet` в команде из README.
2. Получить результат либо понятное сообщение об ошибке входных данных.
3. Открыть локальный отчёт через localhost: увидеть период, охват, ограничения и топ-20.
4. Выбрать строку или ввести полный `gid`; увидеть карточку и направленные связи.
5. Проверить числа и правило каждой совпавшей роли, кластер, основания приоритета и ограничения наблюдения. При включённом P1 доступны дневная активность, следующий запрос данных, маршруты с датами и структурный контекст.
6. Использовать готовые CSV как материал для дальнейшего рассмотрения человеком.

## 4. Экран и поведение

Экран — React/Vite с Cytoscape.js, без UI-kit/router/store. Один selectedGid связывает карточку, таблицы, поиск и граф; JSON загружается с того же localhost. Loading/error/empty видимы; отсутствующий или невалидный JSON не заменяется учебным примером. Node нужен при сборке; runtime использует готовые assets и локальную статическую раздачу. HA-06/07 сохраняют историю исходного standalone HTML, продолжение — HA-15.

| Область | Содержание и поведение |
|---|---|
| Верхняя панель | Период 01–31.07.2026, число узлов/рёбер/транзакций, дата выпуска; сообщение об исходящей четырёхшаговой выборке и пороге 5 000 KZT |
| Топ | Ранг, полный ID, основная роль, приоритет и причина; число клиентов с тем же точным P и переход ко всем таким клиентам, включая вне top-20; выбор открывает тот же узел на графе |
| Поиск | Текстовое поле, точное сравнение строкового ID; Enter запускает поиск; неизвестный ID даёт явное сообщение |
| Карточка | Полный ID, seed/depth, основная и совпавшие вторичные роли с их числами и порогами, поддержка гипотезы, суммы/количества входа и выхода, ведущие основания приоритета, ограничения |
| Граф | Направленные рёбра; толщина по общей логарифмической шкале суммы с легендой и точной суммой в подсказке/таблице; выбор узла и контрагентов; окрестность одного шага по умолчанию; общий граф доступен как круговая карта кластеров |
| Кластеры | Список групп со сводками и фильтр; цветовой режим «роли / кластеры» |
| Фильтры | Роль с явным режимом «основная / любое совпавшее правило», кластер, seed / остальные клиенты; работают по полному индексу, показывают число найденных узлов, не пересчитывают показатели |
| Экспорт | Ссылки на три соседних CSV, созданных текущим запуском; копирование точного ID из карточки |

Карточка последовательно отвечает: **что наблюдалось → какое правило совпало → чего не хватает для вывода**. Выбор узла на графе, в таблице и через поиск открывает одну и ту же карточку. Число прямых seed-плательщиков при добавлении P1 показывается отдельно от числа seed, достигающих узла по пути.

На первом уровне списка и карточки выводятся два ведущих вклада из сохранённых `score_components` и весов отчёта, затем читаемые факты о ролях, связях, обороте и охвате seed. UI поясняет сохранённый приоритет, не пересчитывая его. При раскрытии совпавших правил интерфейс излагает условия словами, беря фактические значения и пороги из JSON; исходные `reason`, `why` и `evidence` доступны отдельно для аудита. В кластере сначала видны состав, частые роли и первый клиент для проверки, исходная `hypothesis` раскрывается по запросу. На узком экране сводка свернута, а после поиска доступны переходы к карточке, связям и списку. Декоративная аббревиатура и статус локального выпуска не занимают место в шапке.

Ориентиры для сценария исследования: [Graphistry Anti-Fraud](https://www.graphistry.com/use-cases/anti-fraud) описывает переход от найденной сущности к связанным узлам и контексту; [Quantexa Graph Analytics](https://www.quantexa.com/platform/graph-analytics/) — динамический просмотр релевантных связей и потоков; [руководство Linkurious](https://doc.linkurious.com/user-manual/latest/page.html) — исследование графа с деталями выбранной сущности. Отсюда выбор одного шага вокруг клиента по умолчанию, соседней карточки и отдельного обзорного режима всего графа; конкретный визуальный стиль остаётся собственным.

Поиск действует по полному индексу, даже если текущий фильтр скрывает узел: показать найденный узел и явно обновить область просмотра. Глобальный rank не заменять новым при фильтрации. Если часть связей скрыта для читаемости, показать счётчик и способ раскрыть их; полные суммы остаются доступными.

HA-17 закрывает уточнения P-03/P-05/P-06 в P0. Масштаб толщины вычисляется по всем рёбрам отчёта и сохраняется при фильтрах; одинаковые суммы имеют одинаковую толщину. Равенство приоритета определяется по полному сохранённому значению, без округления экрана. В CSV остаются ровно 20 строк с прежним разрешением равенства по числовому gid; просмотр равных значений не создаёт им выдуманных глобальных рангов. Для старого отчёта без подробных причин показывается имеющееся evidence и явное отсутствие детализации.

Изолят отображается отдельной вершиной с сообщением об отсутствии наблюдаемых рёбер. Ошибка поиска не оставляет предыдущую карточку под новым введённым ID. Пустой фильтр показывает пустое состояние. Все действия доступны с клавиатуры; цвет дополняется текстом/формой и таблицей связей.

Целевые, пока не измеренные показатели UI: первый полезный экран <5 секунд, поиск <1 секунды. Для сдачи проверить их на демо-ноутбуке, а не объявлять выполненными заранее.

## 5. Формулировки

- `role_score` подписывается «поддержка гипотезы», не «вероятность преступления».
- `coordinator` — гипотеза структурной координации, не установленный организатор.
- `terminal` — кандидат в конечные получатели внутри наблюдаемого периода и фрагмента.
- `peripheral` — специальная роль не установлена; это не заключение о безопасности клиента.
- Связность, большой оборот и достижимость от seed не доказывают общность контроля или происхождение денег.
- Маршрут с датами показывает возможную последовательность наблюдаемых переводов. Он не устанавливает пересылку одной и той же суммы. Совпадение дат не устанавливает порядок внутри дня; отсутствие такого маршрута не означает безопасность клиента.
- На границе графа писать «исходящие за пределами наблюдения», а не «средства остались».
- Сильно связная компонента (SCC) — взаимная достижимость в месячном графе. Она не доказывает хронологический возврат тех же денег, самофинансирование или наличие организатора. SCC и сообщество Louvain — разные структуры и разные подписи в UI.
- 5 000 KZT — нижняя граница выгрузки. Переводы около неё не получают автоматически признак дробления или регуляторный код.
- Низкая оценка вероятности скрытого выхода не разрешает роль terminal на depth=4. Роль и приоритет не получают автоматический бонус за SCC или штраф только за seed/frontier.

## 6. Принятые дополнения P1 и отложенные эксперименты

P0 — обязательный сквозной выпуск по §3, включая HA-17. Стартовый барьер P1 — HA-07.2 + HA-08.1 + HA-15.2 + HA-15.3 + HA-17.2. Принятый порядок целых пар: **HA-11 → HA-14 → HA-16 → HA-13**; HA-12 может готовить оценку baseline независимо. Каждая пара заканчивается рабочим просмотром и проверкой; отсутствие ещё не реализованного P1-поля не ломает отчёт. HA-08.2 принимает окончательный состав функций и не блокирует начало P1. Включение всех P1 до дедлайна не обещается.

| ID / задачи | Дополнение | Поведение и приёмка |
|---|---|---|
| P-11 / HA-11 | Наблюдаемые признаки и дневная активность | Прямые seed-плательщики; максимальное число плательщиков/получателей за день; дневные суммы и counts. Итоги совпадают с исходными переводами. Same-day не описывается как установленная последовательность. |
| P-13 / HA-14 | Следующий запрос данных | Карточка связывает наблюдаемое ограничение с конкретным запросом. Фильтр frontier работает по всей таблице узлов и сортирует её по наблюдаемому входу; основной priority не меняется. |
| P-15 / HA-16 | Маршруты от seed с датами | Отдельные counts достижимости за 1–4 перевода при строго возрастающих датах и при допущении одинакового дня; по одному проверяемому маршруту для каждого режима с датами/суммами. Месячный S и priority сохраняются. Нет маршрута и нет рассчитанного блока — разные состояния. |
| P-12 / HA-13 | Структурный обзор | Узлы обзора — сообщества, стрелки — агрегированные переводы между ними; переход к составу и исходным связям. Отдельная подсветка SCC и её внутренних/входящих/исходящих переводов, числа разных внешних получателей; суммы сверяются с рёбрами. |
| P-14 / HA-12 | Проверка полезности и устойчивости | Слепой review объединения top-20 метода, baseline по обороту и контрольных узлов; качество обоснований, полезность следующей проверки, время задачи и чувствительность параметров. Отличие списков само по себе не считается улучшением. |

В обзоре сообщества можно сортировать по обороту, сохраняя их рассчитанные ID. Размеры SCC и суммы вычисляются из входа. Измеренные в исследовании 85 узлов, 875 внешних рёбер и **642 разных внешних получателя** служат сверкой текущего набора, а не константами интерфейса. Доля оборота к frontier определяется по глубине **узла-получателя**; `edges.depth=4` не является таким фильтром.

Запросы в P-13 — подсказки человеку: следующее исходящее колено, полный вход и остатки, точные временные метки, продление периода либо уточнение покрытия изолята. Причины и условия перечислены в SPEC §10.3. Они не запускают внешнюю интеграцию. У frontier без иных наблюдаемых признаков сохраняется peripheral с явной неизвестностью выхода. Фильтр показывает все найденные узлы, включая отсутствующие в top-20; глобальный rank отображается только для узлов, имеющих его в `top_nodes`.

P-15 допускает ожидание между шагами в пределах всего наблюдаемого июля; это существование маршрута по датам, без сопоставления объёмов. Отдельно после принятого объёма можно исследовать сопоставление сумм за 1–2 последующих дня: каждый тиын используется один раз, same-day рассматривается отдельным предположением, конец месяца — как неполное окно. Изменение ранжирования требует отдельного сравнения baseline и вариантов с временными/структурными признаками по одинаковым критериям review. Текущие веса и пороги остаются явно обозначенным эвристическим baseline.

За пределами принятого P0/P1: вероятностное назначение terminal на границе, автоматическая регуляторная классификация, обучение финансовых ролей без разметки, LLM/агенты в runtime, RAG, внешние AML API, банковская интеграция, авторизация, история кейсов, потоковая обработка и серверная БД. Миллионный граф описывается в README. GPU-замер, удаление узлов и NL-ассистент — будущие эксперименты после проверенного выпуска, с отдельным доказательством пользы.

## 7. Приёмочный сценарий демо

1. Запустить расчёт из raw в новый каталог и показать таймер/результаты проверок.
2. Открыть вычисленный топ и разобрать основную и вторичную роли по реальным числам и порогам; пояснить ведущие основания приоритета и его возможное равенство у нескольких клиентов.
3. Показать крупный вход на depth=4 и объяснить, почему terminal не следует из нулевого выхода; при готовом P-13 показать следующий запрос данных.
4. Найти произвольный `gid`, названный проверяющим; показать карточку и связи.
5. Показать кластер, три CSV и измеренные ограничения/метрики. Для тех же 2–3 клиентов использовать только готовый P1: дневную активность, запрос данных, маршрут с датами либо обзор потоков/SCC. При показе P-15 назвать допущение same-day и отсутствие атрибуции денег. P1 помещается в общий пятиминутный сценарий.

Общая продолжительность — **5 минут по ТЗ трека**. Сохранённый отчёт или запись служат резервом показа, но не заменяют рабочий пересчёт. Основной код должен быть зафиксирован до 18:00 23.09.2026 по Астане; исправления после этого не становятся оцениваемой версией.
