# Спецификация продукта: Jigas — Граф денег

Версия 1.2 · 23.09.2026 · статус: спецификация, реализация в работе; готовность функций подтверждается приёмкой. Приняты React + Vite + vis-network и локальный статический сервер для просмотра. Аналитические решения объединённых blueprint-ов сохранены; миграция интерфейса запланирована в HA-15.

Основания — [blueprint Astra](../HackAlem_AI_Research_Architecture_Blueprint.md) и [сравнение с доказательствами и решениями по объединению](BLUEPRINT_COMPARISON.md). Технические контракты и правила: [SPEC.md](SPEC.md). Очередность и реестр задач: [PLAN.md](PLAN.md). При расхождении исследовательских предложений реализация следует этим спецификациям.

## 1. Пользователь и результат

Пользователь — AML-аналитик банка. Он получает ограниченный граф переводов вокруг известных seed-клиентов и должен выбрать, кого проверять следующим, увидеть основания и определить, какие данные запросить для проверки гипотезы.

Результат MVP: после однократной сборки интерфейса один локальный запуск из трёх Parquet создаёт три CSV, `report.json` и каталог просмотра с `report.html` и локальными ресурсами. Пользователь запускает статический сервер из README и открывает `http://127.0.0.1:8000/report.html`. Все 2 248 клиентов доступны в таблицах и поиске. Выводы обозначают структурные гипотезы для проверки.

## 2. Пользовательский сценарий

1. Указать папку с `nodes.parquet`, `edges.parquet`, `transactions.parquet` в команде из README.
2. Получить результат либо понятное сообщение об ошибке входных данных.
3. Запустить локальный просмотр по README и открыть адрес в браузере: увидеть период, охват, ограничения и топ-20.
4. Выбрать строку или ввести полный `gid`; увидеть карточку и направленные связи.
5. Проверить числа и правило роли, кластер, основания приоритета и ограничения наблюдения. В P1 доступны дневная активность, структурный контекст и следующий запрос данных с объяснением причины.
6. Использовать готовые CSV как материал для дальнейшего рассмотрения человеком.

## 3. Обязательные требования и приёмка

| ID | Требование | Наблюдаемая приёмка |
|---|---|---|
| P-01 | Один воспроизводимый batch-запуск | Из сырых файлов появляются три заполненных CSV, report.json и готовый каталог UI без ручных шагов расчёта; сборка UI выполняется заранее |
| P-02 | Роль каждого узла | Ровно 2 248 уникальных `gid`, включая 19 изолятов; роль, оба скора, кластер и evidence заполнены |
| P-03 | Объяснимые критерии | Для каждой из шести ролей есть правило; три произвольных `gid` объясняются по числам за минуту |
| P-04 | Кластеризация | Каждый узел принадлежит одной группе; у группы размер, seed, внутренний оборот, ключевые узлы и гипотеза |
| P-05 | Приоритет проверки | Не менее 20 уникальных узлов в убывающем порядке приоритета; причины согласованы с основным CSV |
| P-06 | Рабочая визуализация | Стрелки, различимые роли/кластеры, легенда, точный поиск любого `gid`, включая изолят и малую компоненту |
| P-07 | Автономность и скорость | После установки и сборки расчёт и просмотр через localhost работают без интернета, ключей или GPU; полный batch-выпуск <300 секунд |
| P-08 | Корректность ограничений | На depth=4 нулевой выход не создаёт `terminal`; неполный вход seed не считается аномалией сам по себе |
| P-09 | Точность и приватность | ID не округляются, нет обогащения или передачи входа наружу, нет утверждений о виновности |
| P-10 | Сдаваемость | Исходники, README, зависимости, три CSV, диаграмма и пятиминутное демо доступны в предусмотренном организатором порядке |

Оценочный объём фиксирован заданием; программа не должна назначать роли по заранее записанным `gid` или считать число 2 248 заменой проверки множества идентификаторов.

## 4. Экран и поведение

| Область | Содержание и поведение |
|---|---|
| Верхняя панель | Период 01–31.07.2026, число узлов/рёбер/транзакций, дата выпуска; сообщение об исходящей четырёхшаговой выборке и пороге 5 000 KZT |
| Топ | Ранг, полный ID, основная роль, приоритет и причина; выбор строки открывает тот же узел на графе |
| Поиск | Текстовое поле, точное сравнение строкового ID; Enter запускает поиск; неизвестный ID даёт явное сообщение |
| Карточка | Полный ID, seed/depth, основная и совпавшие вторичные роли, поддержка гипотезы, суммы/количества входа и выхода, правило, вклад в приоритет, ограничения |
| Граф | Направленные рёбра; выбор узла и контрагентов; окрестность одного шага по умолчанию; общий граф доступен отдельно |
| Кластеры | Список групп со сводками и фильтр; цветовой режим «роли / кластеры» |
| Фильтры | Роль, кластер, seed / остальные клиенты; показывают число найденных узлов, не пересчитывают показатели |
| Экспорт | Ссылки на три соседних CSV, созданных текущим запуском; копирование точного ID из карточки |

Карточка последовательно отвечает: **что наблюдалось → какое правило совпало → чего не хватает для вывода**. Выбор узла на графе, в таблице и через поиск открывает одну и ту же карточку. Число прямых seed-плательщиков при добавлении P1 показывается отдельно от числа seed, достигающих узла по пути.

Поиск действует по полному индексу, даже если текущий фильтр скрывает узел: показать найденный узел и явно обновить область просмотра. Глобальный rank не заменять новым при фильтрации. Если часть связей скрыта для читаемости, показать счётчик и способ раскрыть их; полные суммы остаются доступными.

Изолят отображается отдельной вершиной с сообщением об отсутствии наблюдаемых рёбер. Ошибка поиска не оставляет предыдущую карточку под новым введённым ID. Пустой фильтр показывает пустое состояние. Все действия доступны с клавиатуры; цвет дополняется текстом/формой и таблицей связей.

При загрузке отчёта показывается ожидание; отсутствующий/невалидный `report.json` или неподдерживаемая версия схемы дают понятную ошибку и действие для повторного запуска. Учебный пример не подставляется вместо отсутствующего результата. Просмотр требует localhost; открытие через `file://` не входит в целевой сценарий. Интернет при просмотре не нужен.

Целевые, пока не измеренные показатели UI: первый полезный экран <5 секунд, поиск <1 секунды. Для сдачи проверить их на демо-ноутбуке, а не объявлять выполненными заранее.

## 5. Формулировки

- `role_score` подписывается «поддержка гипотезы», не «вероятность преступления».
- `coordinator` — гипотеза структурной координации, не установленный организатор.
- `terminal` — кандидат в конечные получатели внутри наблюдаемого периода и фрагмента.
- `peripheral` — специальная роль не установлена; это не заключение о безопасности клиента.
- Связность, большой оборот и достижимость от seed не доказывают общность контроля или происхождение денег.
- На границе графа писать «исходящие за пределами наблюдения», а не «средства остались».
- Сильно связная компонента (SCC) — взаимная достижимость в месячном графе. Она не доказывает хронологический возврат тех же денег, самофинансирование или наличие организатора. SCC и сообщество Louvain — разные структуры и разные подписи в UI.
- 5 000 KZT — нижняя граница выгрузки. Переводы около неё не получают автоматически признак дробления или регуляторный код.
- Низкая оценка вероятности скрытого выхода не разрешает роль terminal на depth=4. Роль и приоритет не получают автоматический бонус за SCC или штраф только за seed/frontier.

## 6. Принятые дополнения P1 и отложенные эксперименты

P0 — обязательный сквозной выпуск по §3. После его интеграционного прогона и проверки контрактов приняты следующие дополнения, в порядке ниже. Каждое заканчивается рабочим просмотром и проверкой; отсутствие ещё не реализованного P1-поля не ломает отчёт. Полная проверка релиза выполняется на окончательном составе функций.

| ID / задачи | Дополнение | Поведение и приёмка |
|---|---|---|
| P-11 / HA-11 | Наблюдаемые признаки и дневная активность | Прямые seed-плательщики; максимальное число плательщиков/получателей за день; дневные суммы и counts. Итоги совпадают с исходными переводами. Same-day не описывается как установленная последовательность. |
| P-12 / HA-13 | Структурный обзор | Узлы обзора — сообщества, стрелки — агрегированные переводы между ними; переход к составу и исходным связям. Отдельная подсветка SCC и её внутренних/входящих/исходящих переводов, числа разных внешних получателей; суммы сверяются с рёбрами. |
| P-13 / HA-14 | Следующий запрос данных | Карточка связывает наблюдаемое ограничение с конкретным запросом. Фильтр frontier работает по всей таблице узлов и сортирует её по наблюдаемому входу; основной priority не меняется. |
| P-14 / HA-12 | Проверка полезности и устойчивости | Слепой review объединения top-20 метода, baseline по обороту и контрольных узлов; качество обоснований, полезность следующей проверки, время задачи и чувствительность параметров. Отличие списков само по себе не считается улучшением. |

В обзоре сообщества можно сортировать по обороту, сохраняя их рассчитанные ID. Размеры SCC и суммы вычисляются из входа. Измеренные в исследовании 85 узлов, 875 внешних рёбер и **642 разных внешних получателя** служат сверкой текущего набора, а не константами интерфейса. Доля оборота к frontier определяется по глубине **узла-получателя**; `edges.depth=4` не является таким фильтром.

Запросы в P-13 — подсказки человеку: следующее исходящее колено, полный вход и остатки, точные временные метки, продление периода либо уточнение покрытия изолята. Причины и условия перечислены в SPEC §10.3. Они не запускают внешнюю интеграцию. У frontier без иных наблюдаемых признаков сохраняется peripheral с явной неизвестностью выхода. Фильтр показывает все найденные узлы, включая отсутствующие в top-20; глобальный rank отображается только для узлов, имеющих его в `top_nodes`.

После этих дополнений можно исследовать сопоставление сумм за 1–2 последующих дня: каждый тиын используется один раз, same-day рассматривается отдельным предположением, конец месяца — как неполное окно. Сначала это дополнительное основание в карточке. Изменение ранжирования требует отдельного сравнения baseline и вариантов с временными/структурными признаками по одинаковым критериям review. Текущие веса и пороги остаются явно обозначенным эвристическим baseline.

За пределами принятого P0/P1: вероятностное назначение terminal на границе, автоматическая регуляторная классификация, обучение финансовых ролей без разметки, LLM/агенты в runtime, RAG, внешние AML API, банковская интеграция, авторизация, история кейсов, потоковая обработка и серверная БД. Миллионный граф описывается в README. GPU-замер, удаление узлов и NL-ассистент — будущие эксперименты после проверенного выпуска, с отдельным доказательством пользы.

## 7. Приёмочный сценарий демо

1. Запустить расчёт из raw в новый каталог и показать таймер/результаты проверок.
2. Открыть вычисленный топ и разобрать сборщика либо распределителя по реальным числам.
3. Показать крупный вход на depth=4 и объяснить, почему terminal не следует из нулевого выхода; при готовом P-13 показать следующий запрос данных.
4. Найти произвольный `gid`, названный проверяющим; показать карточку и связи.
5. Показать кластер, три CSV и измеренные ограничения/метрики. При готовом P-12 использовать обзор потоков/SCC; при готовом P-11 показать дневную активность в той же карточке. P1 помещается в общий пятиминутный сценарий.

Общая продолжительность — **5 минут по ТЗ трека**. Сохранённый отчёт или запись служат резервом показа, но не заменяют рабочий пересчёт. Основной код должен быть зафиксирован до 18:00 23.09.2026 по Астане; исправления после этого не становятся оцениваемой версией.
