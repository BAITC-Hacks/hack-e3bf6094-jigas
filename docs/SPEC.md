## 1. Исполнение и файлы

Основной контейнерный запуск на машине команды: `docker compose build pipeline`, `docker compose run --rm prepare`, `docker compose run --rm pipeline`. Сервис `prepare` извлекает три Parquet из архива организатора, без Python на хосте. Равнозначный запуск для эксперта без Docker после установки зависимостей: `python scripts/prepare_data.py`, затем `python starter.py --data ./data --out ./out`. Оба пути читают те же три Parquet и пишут в `out/`; Docker не должен быть единственным способом проверки.

Выбранный стек: Docker Compose и Python 3.13, pandas, NumPy, PyArrow, NetworkX; один HTML-шаблон и локальный vis-network. Прямые зависимости зафиксированы в `requirements.txt`: pandas 2.2.3, NumPy 2.2.6, PyArrow 25.0.1, NetworkX 3.6.1. Контейнер с этими версиями собран; окончательную проверку полного приложения выполнить после реализации. Удалить неиспользуемый обязательный PageRank starter, чтобы не оставлять скрытую зависимость от SciPy.

Порядок: загрузка → валидация → полный граф → признаки → роли/приоритет → сообщества/сводки → проверка результата → выпуск CSV и HTML. Кластеры могут вычисляться независимо от ролей, `top_gids` формируется после приоритета.

Результат успешного запуска: `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, `report.html`, небольшой `validation.json`. Код возврата 0 означает, что обязательные файлы сформированы и проверены. Ошибка входа/расчёта/записи даёт ненулевой код и этап ошибки. Сначала писать и проверять временный выпуск; не выдавать смешанный набор старых и новых файлов за успешный результат.

## 2. Вход и валидация

| Файл | Поля |
|---|---|
| `nodes.parquet` | `gid:int64`, `depth:int`, `is_seed:bool` |
| `edges.parquet` | `src:int64`, `dst:int64`, `sum_kzt:float64`, `n_tx:int64`, `depth:int8` |
| `transactions.parquet` | `src:int64`, `dst:int64`, `date:date`, `sum_kzt:float64` |

Проверки T-01:

- Обязательные поля присутствуют и имеют совместимые типы; отсутствующие значения в них запрещены. ID не проходят через float.
- `gid` уникален; пары `(src,dst)` в edges уникальны; все endpoints имеются в nodes, в том числе endpoints транзакций.
- `nodes.depth` в 0–4, `edges.depth` в 1–4, `is_seed` согласован с `depth=0`; даты разбираются и входят в июль 2026.
- Суммы конечные и положительные; транзакции ≥5 000 KZT; `n_tx` — положительное целое.
- Проверить точность до тиына, затем использовать целые `sum_tiyn=round(sum_kzt*100)`. Допуск представления исходного float документировать; сравнения агрегатов выполнять в целых тиынах.
- Группировка транзакций по паре должна совпадать с edges **по набору пар, сумме и количеству**. Сверка только наличия пар недостаточна.
- Совпадающие строки транзакций не удалять: у входа нет `transaction_id`, а одинаковая дата/сумма/пара не доказывает дубль.

Контрольные свойства официального архива: 2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed, 19 изолятов; оборот **36 589 001 201 тиын**. Полный граф имеет 35 слабых компонент, 444 узла depth=4 без исходящих. Это контроль приёмки на выданном наборе, не списки ответов и не ограничения внутренних тестовых графов.

## 3. Признаки

T-02: сначала добавить **все** `nodes.gid` в `DiGraph`, затем направленные агрегированные рёбра. Не строить граф перезаписью отдельных транзакций.

| Поле | Определение |
|---|---|
| `in_deg`, `out_deg` | Число различных соседей по направлению |
| `in_tiyn`, `out_tiyn` | Суммы наблюдаемых входящих/исходящих |
| `in_tx`, `out_tx` | Сумма `n_tx` в соответствующем направлении |
| `pass_through` | `out_tiyn/in_tiyn`; при нулевом входе — неизвестно, не 0 |
| `boundary` | `depth=4` и `out_deg=0` |
| `isolated` | Обе степени равны 0 |
| `seed_reach_count` (`S`) | Число различных seed, достигающих узла за 1–4 направленных шага; сам узел исключён |
| `betweenness` (`B`) | Точная, направленная, невзвешенная, `normalized=True`, `endpoints=False` |
| `last_in` | Максимальная календарная дата входящей транзакции, иначе неизвестно |
| `days_after_last_in` (`D`) | Разность 31.07.2026 и `last_in` в календарных днях, иначе неизвестно |

Для `S`: отдельный ограниченный BFS на каждый seed, без многократного счёта из-за циклов; при необходимости сохранить один маршрут-свидетель. `sum_kzt` не использовать как расстояние при betweenness. Время внутри дня неизвестно.

## 4. Роли и поддержка

T-03: порядок выбора основной роли: **coordinator → distributor → consolidator → transit → terminal → peripheral**. Рассчитывать также все совпавшие роли; UI показывает их как вторичные. Квантиль — по полному графу, `linear`.

| Роль | Условие | `u` | `cap` |
|---|---|---|---:|
| coordinator | `S≥2`, `in_deg≥2`, `out_deg≥2`, `B>0`, `B≥Q90(B>0)` | `min(1,S/4)` | 0.60 |
| distributor | `out_deg≥10` | `min(1,out_deg/20)` | 0.90 |
| consolidator | `in_deg≥3` | `min(1,in_deg/6)` | 0.90 |
| transit | Не seed, depth<4, вход/выход положительны, `0.8≤r≤1.2` | `max(0,1-abs(r-1)/0.2)` | 0.65 |
| terminal | Не seed, depth<4, вход>0, out_deg=0, D≥2 | `min(1,D/7)` | 0.50 |
| peripheral | Нет совпадений | — | — |

Для каждого совпавшего правила `support=cap*(0.5+0.5*u)`. `role_score` — support **основной** роли; для peripheral 0. Если множество положительных B пусто, coordinator не срабатывает. Не использовать `NaN` как истинное условие.

Это зафиксированный baseline эвристик, а не калиброванные вероятности. Изменение порога требует общего правила, версии параметров и записи причины; не допускаются исключения по ID.

Границы: depth=4 не может стать terminal по нулевому выходу, но может быть consolidator по наблюдаемым входящим. Seed не становится transit/terminal на основе неполного входа. Изолят остаётся peripheral со своим кластером. `O>I` не создаёт дополнительной обвинительной роли.

## 5. Приоритет и объяснение

T-04: `P=0.35*M+0.30*A+0.20*C+0.15*H`.

- `M` — максимум support по всем совпавшим ролям, иначе 0.
- **`V_kzt=(in_tiyn+out_tiyn)/100`**; `A=min(1,log1p(V_kzt)/log1p(Q95(V_kzt>0)))`. Единица нормировки — KZT; нельзя незаметно заменить её тиынами внутри логарифма.
- `C=min(1,S/5)`.
- `H=min(1,B/Q95(B>0))`.
- При пустом положительном множестве/нулевом знаменателе соответствующая компонента 0. Каждый компонент конечен и в [0,1].

Сортировка: полный неокруглённый P по убыванию, точный числовой `gid` по возрастанию. Округление только для экрана. Сохранять компоненты и пороги для проверки.

`evidence`: человеческий текст до 200 Unicode-символов, как минимум числовое основание и значимое ограничение. Формировать из тех же метрик; не обрезать строку посередине числа/смысла. `why`: два ведущих основания приоритета и ограничение. Нулевой объём/отсутствие рёбер — тоже числовое объяснение. Шаблонный текст не должен приписывать клиенту вину.

## 6. Сообщества

T-05: ненаправленный вес `{u,v}` равен сумме обоих направлений **в KZT**; это отдельная проекция, исходные направления сохраняются. Использовать Louvain `resolution=1`, `seed=42` и отсортированный ввод. Изолятам дать отдельные группы. Несвязное сообщество разделить на связные компоненты проекции.

`cluster_id`: группы сортируются по минимальному числовому gid, затем получают номера **0..K−1**. Номера воспроизводимы для фиксированного набора, не обязаны сохраняться при изменении входа.

Сводка: `n_nodes`, `n_seed`, внутренний оборот по исходным направленным рёбрам, до пяти лучших gid по P и осторожная гипотеза с числами. Внешний оборот не включается во внутренний. Сумма внутренних и межкластерного оборотов равна общему. Группа без seed не объявляется безопасной.

## 7. CSV-контракты

UTF-8, заголовки, разделитель запятая, корректное quoting, точка в дробных числах. Полные ID — десятичная запись без экспоненты/`.0`. Обязательные поля не пусты; не добавлять индекс DataFrame как колонку.

| Файл | Обязательные поля и порядок |
|---|---|
| nodes_roles.csv | `gid,role,role_score,cluster_id,priority_score,evidence` |
| clusters.csv | `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis` |
| top_nodes.csv | `rank,gid,role,priority_score,why` |

T-06: nodes отсортированы по числовому gid, clusters — по cluster_id. Scores — конечные числа [0,1]. `top_gids` — JSON-массив **строк**, корректно заключённый в CSV-ячейку. `sum_kzt_internal` выводится в KZT с двумя знаками. Дополнительные документированные поля допустимы после обязательных.

Для официального входа top_nodes содержит первые **20** узлов, rank=1..20. На малом внутреннем тестовом графе допустим top `min(20,N)`; это не ослабляет приёмку официального набора. Роль и P каждой строки совпадают с nodes_roles. Нет отдельного «демонстрационного» расчёта топа.

## 8. Контракт HTML / Python

T-07: Python формирует один объект для отчёта; JavaScript отвечает за просмотр и фильтрацию, не присваивает роли заново. Результат встраивается в HTML, внешние запросы `fetch` для данных не нужны.

| Ключ | Содержимое |
|---|---|
| `schema_version` | Строка `1.0` |
| `dataset` | Период, размеры входа, оборот в тиынах, SHA-256 каждого входного файла |
| `parameters` | Версия правил, пороги, веса, квантили, seed и resolution |
| `nodes[]` | `gid:string`, role, role_score, cluster_id, priority_score, evidence; все признаки §3, matched_roles, score_components, warnings |
| `edges[]` | `src:string`, `dst:string`, `sum_tiyn:int`, `n_tx:int`, depth |
| `clusters[]` | Свойства сводки; `top_gids` как массив строк, не повторно закодированный JSON |
| `top_nodes[]` | rank, `gid:string`, role, priority_score, why |

`score_components={M,A,C,H}` содержит нормированные значения; веса лежат в parameters. `matched_roles` содержит список совпавших правил и их support. `warnings` содержит коды `boundary`, `seed_incomplete_in`, `isolated`, `short_followup` по применимости; общая неполнота графа сообщается на уровне отчёта. Даты — `YYYY-MM-DD` либо `null`.

**Все ID преобразуются в строки до JSON.** Не использовать JS Number/parseInt для `gid/src/dst`. Текущие суммы в тиынах укладываются в безопасный целочисленный диапазон JS; перед сериализацией это проверяется. Неопределённые величины — `null`, не `NaN/Infinity`. Экранировать встраиваемый JSON и HTML; текст карточек выводить через безопасные текстовые узлы.

T-08: vis-network фиксированной версии и лицензия хранятся локально; JS/CSS включены в отчёт. Нет CDN, шрифтов/телеметрии/аналитики с внешними запросами. Браузер должен открыть отчёт и CSV из каталога выпуска без сервера. Поиск/фильтры/состояния — по PRODUCT_SPEC §4.

Критерии качества ролей проверяются ручным review и сравнением с baseline. Ground truth нет: accuracy/F1 и вероятность преступления не заявляются. Тесты правил не являются измерением AML-точности.

## 10. Изменения и P1

P1 добавляет дневные агрегаты в карточку, не меняя основного CSV-контракта или смысла score. Сопоставление потоков по датам — отдельная функция только после проверки невозвратного расходования объёма и конца месяца. Источники/ограничения остаются видимыми.

Обратимо менять параметры допустимо до заморозки по результатам проверки, с обновлением версии, спецификации и связанных задач. ID-исключения, замена входа внешним датасетом и неотражённое изменение формулы запрещены. Все ещё не реализованные функции остаются задачами, а не отмечаются готовыми по наличию этой спецификации.
