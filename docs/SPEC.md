## 1. Исполнение и файлы

Основной контейнерный запуск на машине команды: `docker compose build pipeline`, `docker compose run --rm prepare`, `docker compose run --rm pipeline`. Сервис `prepare` извлекает три Parquet из архива организатора, без Python на хосте. Равнозначный запуск для эксперта без Docker после установки зависимостей: `python scripts/prepare_data.py`, затем `python starter.py --data ./data --out ./out`. Оба пути читают те же три Parquet и пишут в `out/`; Docker не должен быть единственным способом проверки.

Выбранный стек: Docker Compose и Python 3.13, pandas, NumPy, PyArrow, NetworkX; один HTML-шаблон и локальный vis-network. Прямые зависимости зафиксированы в `requirements.txt`: pandas 2.2.3, NumPy 2.2.6, PyArrow 25.0.1, NetworkX 3.6.1. Контейнер с этими версиями собран; окончательную проверку полного приложения выполнить после реализации. Удалить неиспользуемый обязательный PageRank starter, чтобы не оставлять скрытую зависимость от SciPy.

Порядок: загрузка → валидация → полный граф → признаки → роли/приоритет → сообщества/сводки → проверка результата → выпуск CSV и HTML. Кластеры могут вычисляться независимо от ролей, `top_gids` формируется после приоритета.

Реализованные P1-признаки и структурный контекст добавляются после назначения кластеров, до сборки/проверки общего отчёта. Их читает тот же HTML. У них нет собственного расчёта ролей, приоритета или второго выпуска CSV; основной запуск остаётся одним CLI без сервера и дополнительных библиотек.

Результат успешного запуска: `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, `report.html`, небольшой `validation.json`. Код возврата 0 означает, что обязательные файлы сформированы и проверены. Ошибка входа/расчёта/записи даёт ненулевой код и этап ошибки. Сначала писать и проверять временный выпуск; не выдавать смешанный набор старых и новых файлов за успешный результат.

## 2. Вход и валидация

| Файл | Поля |
|---|---|
| `nodes.parquet` | `gid:int64`, `depth:int`, `is_seed:bool` |
| `edges.parquet` | `src:int64`, `dst:int64`, `sum_kzt:float64`, `n_tx:int64`, `depth:int8` |
| `transactions.parquet` | `src:int64`, `dst:int64`, `date:date`, `sum_kzt:float64` |

Проверки T-01:

- Обязательные поля присутствуют и имеют совместимые типы; отсутствующие значения в них запрещены. ID не проходят через float.
- `gid` уникален; пары `(src,dst)` в edges уникальны; все endpoints имеются в nodes, в том числе endpoints транзакций.
- `nodes.depth` в 0–4, `edges.depth` в 1–4, `is_seed` согласован с `depth=0`; даты разбираются и входят в июль 2026.
- Суммы конечные и положительные; транзакции ≥5 000 KZT; `n_tx` — положительное целое.
- Проверить точность до тиына, затем использовать целые `sum_tiyn=round(sum_kzt*100)`. Допуск представления исходного float документировать; сравнения агрегатов выполнять в целых тиынах.
- Группировка транзакций по паре должна совпадать с edges **по набору пар, сумме и количеству**. Сверка только наличия пар недостаточна.
- Совпадающие строки транзакций не удалять: у входа нет `transaction_id`, а одинаковая дата/сумма/пара не доказывает дубль.

Контрольные свойства официального архива: 2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed, 19 изолятов; оборот **36 589 001 201 тиын**. Полный граф имеет 35 слабых компонент, 444 узла depth=4 без исходящих. Это контроль приёмки на выданном наборе, не списки ответов и не ограничения внутренних тестовых графов.

`nodes.depth` — глубина узла, `edges.depth` — шаг обнаружения ребра. В текущем архиве `edges.depth = nodes.depth[src] + 1`; получатель может находиться на более раннем слое. Поступления на frontier всегда фильтруются через `nodes.depth[dst] == 4`.

## 3. Признаки

T-02: сначала добавить **все** `nodes.gid` в `DiGraph`, затем направленные агрегированные рёбра. Не строить граф перезаписью отдельных транзакций.

| Поле | Определение |
|---|---|
| `in_deg`, `out_deg` | Число различных соседей по направлению |
| `in_tiyn`, `out_tiyn` | Суммы наблюдаемых входящих/исходящих |
| `in_tx`, `out_tx` | Сумма `n_tx` в соответствующем направлении |
| `pass_through` | `out_tiyn/in_tiyn`; при нулевом входе — неизвестно, не 0 |
| `boundary` | `depth=4` и `out_deg=0` |
| `isolated` | Обе степени равны 0 |
| `seed_reach_count` (`S`) | Число различных seed, достигающих узла за 1–4 направленных шага; сам узел исключён |
| `betweenness` (`B`) | Точная, направленная, невзвешенная, `normalized=True`, `endpoints=False` |
| `last_in` | Максимальная календарная дата входящей транзакции, иначе неизвестно |
| `days_after_last_in` (`D`) | Разность 31.07.2026 и `last_in` в календарных днях, иначе неизвестно |

Для `S`: отдельный ограниченный BFS на каждый seed, без многократного счёта из-за циклов; при необходимости сохранить один маршрут-свидетель. `sum_kzt` не использовать как расстояние при betweenness. Время внутри дня неизвестно.

Входящий профиль неполон для любого узла. Исходящие глубин 0–3 наблюдаются только в пределах банка, июля и порога выгрузки; это не полный финансовый баланс. Наблюдаемые признаки P1 определены в §10 и не подменяют эти ограничения.

## 4. Роли и поддержка

T-03: порядок выбора основной роли: **coordinator → distributor → consolidator → transit → terminal → peripheral**. Рассчитывать также все совпавшие роли; UI показывает их как вторичные. Квантиль — по полному графу, `linear`.

| Роль | Условие | `u` | `cap` |
|---|---|---|---:|
| coordinator | `S≥2`, `in_deg≥2`, `out_deg≥2`, `B>0`, `B≥Q90(B>0)` | `min(1,S/4)` | 0.60 |
| distributor | `out_deg≥10` | `min(1,out_deg/20)` | 0.90 |
| consolidator | `in_deg≥3` | `min(1,in_deg/6)` | 0.90 |
| transit | Не seed, depth<4, вход/выход положительны, `0.8≤r≤1.2` | `max(0,1-abs(r-1)/0.2)` | 0.65 |
| terminal | Не seed, depth<4, вход>0, out_deg=0, D≥2 | `min(1,D/7)` | 0.50 |
| peripheral | Нет совпадений | — | — |

Для каждого совпавшего правила `support=cap*(0.5+0.5*u)`. `role_score` — support **основной** роли; для peripheral 0. Если множество положительных B пусто, coordinator не срабатывает. Не использовать `NaN` как истинное условие.

Это зафиксированный baseline эвристик, а не калиброванные вероятности. Изменение порога требует общего правила, версии параметров и записи причины; не допускаются исключения по ID.

Границы: depth=4 не может стать terminal по нулевому выходу, но может быть consolidator по наблюдаемым входящим. Seed не становится transit/terminal на основе неполного входа. Изолят остаётся peripheral со своим кластером. `O>I` не создаёт дополнительной обвинительной роли.

Оценка скрытого выхода по бакетам/ML не отменяет запрета terminal на frontier. SCC и число сообществ плательщиков — контекст для проверки, а не дополнительные голоса в coordinator. Первичная роль выбирается по precedence; все вторичные совпадения сохраняются. Нулевая поддержка peripheral обозначает неустановленную роль, включая изолят.

## 5. Приоритет и объяснение

T-04: `P=0.35*M+0.30*A+0.20*C+0.15*H`.

- `M` — максимум support по всем совпавшим ролям, иначе 0.
- **`V_kzt=(in_tiyn+out_tiyn)/100`**; `A=min(1,log1p(V_kzt)/log1p(Q95(V_kzt>0)))`. Единица нормировки — KZT; нельзя незаметно заменить её тиынами внутри логарифма.
- `C=min(1,S/5)`.
- `H=min(1,B/Q95(B>0))`.
- При пустом положительном множестве/нулевом знаменателе соответствующая компонента 0. Каждый компонент конечен и в [0,1].

Сортировка: полный неокруглённый P по убыванию, точный числовой `gid` по возрастанию. Округление только для экрана. Сохранять компоненты и пороги для проверки.

P1 не добавляет множители только за seed/frontier и не использует SCC, близость суммы к 5 000 KZT или непроверенные вероятности для изменения P. 5 000 KZT — порог выгрузки, не установленный этим набором регуляторный порог. Автоматические юридические коды в evidence/why/hypothesis не присваиваются.

`evidence`: человеческий текст до 200 Unicode-символов, как минимум числовое основание и значимое ограничение. Формировать из тех же метрик; не обрезать строку посередине числа/смысла. `why`: два ведущих основания приоритета и ограничение. Нулевой объём/отсутствие рёбер — тоже числовое объяснение. Шаблонный текст не должен приписывать клиенту вину.

## 6. Сообщества

T-05: ненаправленный вес `{u,v}` равен сумме обоих направлений **в KZT**; это отдельная проекция, исходные направления сохраняются. Использовать Louvain `resolution=1`, `seed=42` и отсортированный ввод. Изолятам дать отдельные группы. Несвязное сообщество разделить на связные компоненты проекции.

`cluster_id`: группы сортируются по минимальному числовому gid, затем получают номера **0..K−1**. Номера воспроизводимы для фиксированного набора, не обязаны сохраняться при изменении входа.

Сводка: `n_nodes`, `n_seed`, внутренний оборот по исходным направленным рёбрам, до пяти лучших gid по P и осторожная гипотеза с числами. Внешний оборот не включается во внутренний. Сумма внутренних и межкластерного оборотов равна общему. Группа без seed не объявляется безопасной.

## 7. CSV-контракты

UTF-8, заголовки, разделитель запятая, корректное quoting, точка в дробных числах. Полные ID — десятичная запись без экспоненты/`.0`. Обязательные поля не пусты; не добавлять индекс DataFrame как колонку.

| Файл | Обязательные поля и порядок |
|---|---|
| nodes_roles.csv | `gid,role,role_score,cluster_id,priority_score,evidence` |
| clusters.csv | `cluster_id,n_nodes,n_seed,sum_kzt_internal,top_gids,hypothesis` |
| top_nodes.csv | `rank,gid,role,priority_score,why` |

T-06: nodes отсортированы по числовому gid, clusters — по cluster_id. Scores — конечные числа [0,1]. `top_gids` — JSON-массив **строк**, корректно заключённый в CSV-ячейку. `sum_kzt_internal` выводится в KZT с двумя знаками. Дополнительные документированные поля допустимы после обязательных.

Для официального входа top_nodes содержит первые **20** узлов, rank=1..20. На малом внутреннем тестовом графе допустим top `min(20,N)`; это не ослабляет приёмку официального набора. Роль и P каждой строки совпадают с nodes_roles. Нет отдельного «демонстрационного» расчёта топа.

## 8. Контракт HTML / Python

T-07: Python формирует один объект для отчёта; JavaScript отвечает за просмотр и фильтрацию, не присваивает роли заново. Результат встраивается в HTML, внешние запросы `fetch` для данных не нужны.

| Ключ | Содержимое |
|---|---|
| `schema_version` | Строка `1.0` |
| `dataset` | Период, размеры входа, оборот в тиынах, SHA-256 каждого входного файла |
| `parameters` | Версия правил, пороги, веса, квантили, seed и resolution |
| `nodes[]` | `gid:string`, role, role_score, cluster_id, priority_score, evidence; все признаки §3, matched_roles, score_components, warnings |
| `edges[]` | `src:string`, `dst:string`, `sum_tiyn:int`, `n_tx:int`, depth |
| `clusters[]` | Свойства сводки; `top_gids` как массив строк, не повторно закодированный JSON |
| `top_nodes[]` | rank, `gid:string`, role, priority_score, why |
| `daily_profiles_by_gid` · P1 | Необязательный словарь дневных наблюдений по §10.1; ключи — строковые gid |
| `community_edges[]`, `sccs[]`, `coverage` · P1 | Необязательные структурные сводки по §10.2 |
| `boundary_gids_by_inflow:string[]` · P1 | Необязательный индекс frontier для представления запросов по §10.3 |

`score_components={M,A,C,H}` содержит нормированные значения; веса лежат в parameters. `matched_roles` содержит список совпавших правил и их support. `warnings` содержит коды `boundary`, `seed_incomplete_in`, `isolated`, `short_followup` по применимости; общая неполнота графа сообщается на уровне отчёта. Даты — `YYYY-MM-DD` либо `null`.

Дополнительные поля `nodes[]` перечислены в §10. Они не обязательны для P0. UI проверяет наличие соответствующего блока; отсутствующий признак не превращается в 0 и не объявляется рассчитанным. Неизвестные дополнительные поля можно игнорировать; смысл и типы базовых полей `1.0` не меняются. Метаданные `parameters` записывают фактически реализованные группы P1 и их определения, без флагов готовности для ещё не созданных функций.

**Все клиентские ID преобразуются в строки до JSON.** Не использовать JS Number/parseInt для `gid/src/dst`; рассчитанные cluster_id/scc_id остаются небольшими целыми. Текущие суммы в тиынах укладываются в безопасный целочисленный диапазон JS; перед сериализацией это проверяется. Неопределённые величины — `null`, не `NaN/Infinity`. Экранировать встраиваемый JSON и HTML; текст карточек выводить через безопасные текстовые узлы.

T-08: vis-network фиксированной версии и лицензия хранятся локально; JS/CSS включены в отчёт. Нет CDN, шрифтов/телеметрии/аналитики с внешними запросами. Браузер должен открыть отчёт и CSV из каталога выпуска без сервера. Поиск/фильтры/состояния — по PRODUCT_SPEC §4.

До сдачи выполнить пять полных запусков из raw; показать median/maximum и характеристики машины. Порог <300 секунд относится ко всем обязательным CSV; внутренний тест включает также HTML. При реализации P1 тот же проверочный сценарий дополняется сверкой дневных сумм/counts с узлами, направленных межкластерных сумм с исходными рёбрами, членства/сводок SCC и условий запросов данных. Проверить UI как с доступными P1-блоками, так и на минимальном P0-объекте. Размеры SCC, состав top-20 и число ролей не задаются в логике константами. Полная приёмка HA-08.2 выполняется после последнего принятого изменения; уже пройденные проверки повторяются при изменениях, затрагивающих их результат.

## 10. Принятые дополнения P1

Дополнения реализуются после успешных HA-07.2 и HA-08.1, до заморозки новых функций; HA-08.2 принимает окончательный состав выпуска. Все суммы — целые тиыны, все клиентские ID в JSON — строки. Нет новых обязательных CSV, зависимостей или отдельного UI. Порядок функций — HA-11 → HA-13 → HA-14; оценка HA-12 может начинаться с доступного baseline.

### 10.1. Наблюдаемые признаки и дневные профили — HA-11

| Дополнительное поле узла | Определение |
|---|---|
| `n_seed_payers:int` | Число разных непосредственных предшественников в G с `is_seed=True`; не число seed-путей и не число сообществ |
| `sync_payers_max:int` | Максимум числа различных src по `(dst,date)` в transactions; 0 при отсутствии входящих |
| `fanout_burst_max:int` | Максимум числа различных dst по `(src,date)`; 0 при отсутствии наблюдаемых исходящих |

`daily_profiles_by_gid[gid]` — список `{date,in_tiyn,out_tiyn,in_tx,out_tx,n_payers,n_payees}` по дням хотя бы с одной наблюдаемой операцией, в возрастающем порядке. Ключ есть у каждого узла; у изолята список пуст. В строке отсутствующее направление даёт 0; для отображения календарной оси UI может заполнить пропущенные дни нулями наблюдений только у выбранного узла. Число контрагентов считается по уникальным ID, counts — по всем строкам transactions, включая совпадающие. Сумма дневных in/out и counts совпадает с узловыми агрегатами; дневные числа уникальных плательщиков нельзя складывать как месячный in_deg.

Нули обозначают отсутствие операций в выгрузке. У frontier исходящий профиль сопровождается указанием, что исходящие не наблюдались. Синхронность по дате не устанавливает порядок операций или время удержания. Дневной профиль показывается в существующей карточке через HTML/SVG/таблицу без новой библиотеки.

### 10.2. Сообщества, SCC и покрытие — HA-13

- `nodes[].n_payer_comms:int` — число разных `cluster_id` непосредственных плательщиков, включая собственное сообщество, если из него есть вход; 0 у узла без входа.
- `community_edges[]` — `{src_cluster_id,dst_cluster_id,sum_tiyn,n_edges,n_tx}`. Одна строка на упорядоченную пару **разных** сообществ; встречные направления раздельны. `n_edges` — число исходных агрегированных рёбер, `n_tx` — сумма их counts. Сортировка по двум ID. Внутренний оборот берётся из `clusters[]`; его сумма плюс сумма `community_edges.sum_tiyn` равна обороту графа.
- SCC вычисляются в исходном направленном G, включая singleton-компоненты. `scc_id` задаётся по минимальному числовому gid, аналогично cluster_id, но в отдельном пространстве. Каждый узел получает `scc_id:int,scc_size:int`; связные сообщества Louvain не заменяют SCC.
- `sccs[]` — `{scc_id,n_nodes,n_seed,n_edges_internal,n_edges_incoming,n_edges_outgoing,sum_tiyn_internal,sum_tiyn_incoming,sum_tiyn_outgoing,n_external_recipients,origin_turnover_share}`. Вход/выход учитывает только пересечение границы данной SCC; внутренние рёбра считаются отдельно. Получатели — уникальные dst вне SCC. `origin_turnover_share=(internal+outgoing)/общий_оборот`, при нулевом обороте 0. Строки по scc_id; состав определяется через поля узлов, повторный список gid не нужен.
- `coverage` — `{boundary_n_nodes,sum_tiyn_to_boundary,share_to_boundary}` по узлам depth=4 и исходным рёбрам к ним. При нулевом общем обороте доля 0. Нулевая наблюдаемая исходящая активность не трактуется как удержание денег.

UI рисует направленный мета-граф по `clusters[]` и `community_edges[]`; выбор открывает состав и исходные связи. Отдельный режим подсветки SCC использует тот же узловой граф. По умолчанию SCC-обзор выбирает наибольшую компоненту с `n_nodes>1`, при равенстве минимальный scc_id; если таких нет, это явно сообщается. Клик по агрегированной связи раскрывает соответствующие исходные рёбра. Все сводные суммы вычисляет Python; UI фильтрует и форматирует результат.

Сверки текущего официального входа из [аудита](../research/blueprint_comparison_evidence.json): крупнейшая SCC — 85 узлов, 2 seed, 242 внутренних ребра на 19 453 337,04 KZT; 875 внешних исходящих рёбер на 90 230 006,09 KZT к **642** разным получателям; 7 внешних входящих рёбер на 705 193,00 KZT. Доля оборота, исходящего от членов SCC, — 29,98%, включая внутренние переводы. Поступления на frontier — **56 672 164,68 KZT / 15,49%**. Это эталоны сверки агрегатов для этих файлов, не условия классификации и не доказательство преступной структуры.

### 10.3. Следующий запрос данных — HA-14

`nodes[].next_data_requests` — список `{reason_code:string,text:string}`, рассчитанный Python по таблице ниже в указанном порядке. Применяются все подходящие условия; пустой список допустим. В тексте указать наблюдаемое основание и запрос, без выдуманных сведений о клиенте. Это подсказка для человека, не сетевой вызов.

| reason_code | Условие | Запрос |
|---|---|---|
| `boundary` | depth=4 | Следующий исходящий слой для выбранного узла с указанием банка, периода и порога; текущий выход неизвестен |
| `short_followup` | in_tiyn>0, out_deg=0, days_after_last_in<2 | Продлить окно минимум до двух дней после последнего поступления; указать дату поступления |
| `incomplete_balance` | Есть наблюдаемые входящие или исходящие | Полный вход и начальный/конечный остатки для проверки баланса; текущие суммы ограничены выборкой |
| `same_day_order` | Есть день с in_tx>0 и out_tx>0 в дневном профиле | Временные метки переводов для проверки порядка внутри дня; указать первую такую дату |
| `isolated` | in_deg=out_deg=0 | Уточнить покрытие выгрузки по этому gid, включая операции вне банка/периода/порога; отсутствие записей не объясняет причину |

Представление «Запросить продолжение» — фильтр **всех** узлов depth=4, сортировка in_tiyn ↓, затем точный числовой gid ↑, рассчитанная Python или порядком строк из Python для UI. Строковые ID не сравнивать через JS Number. Для этого P1-блока Python передаёт `boundary_gids_by_inflow:string[]` в указанном порядке; это индекс существующих узлов, не ещё один скор или CSV. Исходный priority_score и глобальные ранги top_nodes сохраняются. У узла вне top_nodes глобальный rank отсутствует и не придумывается.

### 10.4. Оценка и последующие изменения — HA-12

Baseline — формула §5 и отдельный топ по `in_tiyn+out_tiyn`. Review получает объединение двух top-20 и контрольную выборку с фиксированным seed, без названия метода и ранга. Фиксируются проверяемость оснований, корректность направления/неполноты, полезность следующего запроса, время задачи, размер выборки и компетенция рецензента. Overlap и доля non-seed описывают выборку, но сами по себе не измеряют полезность. Устойчивость — изменения порогов/весов ±20% с перенормировкой весов; для сообществ сравнивать членство, не только число групп.

Добавление контекста в P1 не меняет top-20. Предлагаемый новый скор сравнивается отдельно: исходный baseline → вариант с временными признаками → со структурными → объединённый. Определения/веса и критерии review фиксируются до просмотра результата; выигрыш обосновывается review, а не отличием списков или повышением встроенных в скор метрик.

Следующий временной эксперимент переиспользует проверенный подход из `research/compare_blueprints.py`: FIFO с расходованием каждого тиына входа и выхода не более одного раза, окно **1–2 последующих календарных дня**. Сопоставленный объём делится на наблюдаемый исходящий; при отсутствии выхода результат неизвестен (`null`). Same-day допускается только отдельным явно названным предположением. При доле пересланного входа исключать из знаменателя поступления без полного последующего окна и показывать их отдельно. Сигнал «есть любое поступление за 0–2 дня до выхода» можно считать совпадением по времени, но нельзя называть FIFO. Перед включением в продукт проверить суммы, повторное использование, same-day и конец периода; продемонстрированные исследовательские количества не являются эталоном AML-ролей.

Обратимо менять параметры допустимо до заморозки по результатам проверки, с обновлением версии, спецификации и связанных задач. ID-исключения, замена входа внешним датасетом и неотражённое изменение формулы запрещены. Все ещё не реализованные функции остаются задачами, а не отмечаются готовыми по наличию этой спецификации.
